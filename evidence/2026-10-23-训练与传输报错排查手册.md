## 一、训练阶段

### 1.1 `HFValidationError: Repo id must be in the form 'repo_name' or 'namespace/repo_name'`

**完整报错**

```
huggingface_hub.errors.HFValidationError:
Repo id must be in the form 'repo_name' or 'namespace/repo_name':
'/root/work/grasp-main-5000-v2/warmstart-hf'.
Use `repo_type` argument if needed.
```

**原因**

`training.yaml` 里的 `model.model_path` / `model.config_path` 指向了一个**已经在本地盘上被删掉**的路径。
transformers 把 `/root/work/...` 当成 HuggingFace repo id 去解析，所以报"格式不对"。
真正的错误是"文件不存在"，但报错信息极具误导性。

**修复**

把两个字段都改成团队盘上的稳定路径：

```yaml
model:
  model_path: /teams/A100_zone_1791964949/models/robbyant_lingbot-vla-v2-6b
  config_path: /teams/A100_zone_1791964949/models/robbyant_lingbot-vla-v2-6b
```

**教训**

- 报 "Repo id must be in the form..." 时，**先检查路径是否真的存在**，别去查 HF 认证
- 训练配置里凡是路径，优先用团队盘（`/teams/...`）而不是本地盘（`/root/work/...`）

### 1.2 `FileExistsError: /root/work/cont1020/warmstart-hf`

**完整报错**

```
FileExistsError: [Errno 17] File exists: '/root/work/cont1020/warmstart-hf'
```

**原因**

上一次运行被静默杀掉（`nohup ... &` 没捕获输出），留下了**空目录**，第二次启动时 `os.makedirs` 冲突。

**修复**

```bash
rm -rf /root/work/cont1020/warmstart-hf
```

**教训**

- 不要用 `nohup cmd > log 2>&1 &` 直接跑关键命令 —— 它会把 Python 的 stdout 缓冲吞掉，崩溃时日志只有一行 `nohup: ignoring input`
- 改用 `setsid nohup cmd > log 2>&1 < /dev/null &`，或者先 `timeout 180 bash start.sh > /tmp/verify.log 2>&1` 验证能起来

### 1.3 `train_lingbotvla` 静默崩溃，日志无任何输出

**现象**

```
nohup: ignoring input
（日志到此为止）
```

**原因**

1. `nohup ... &` 吞掉了 stdout
2. 真实错误在 Python 的 stderr 缓冲里，进程被 SIGTERM 时未 flush

**诊断方法**

```bash
# ❌ 错误：管道 + timeout，SIGTERM 时缓冲区丢失
timeout 180 bash /root/start.sh | tail -30

# ✅ 正确：重定向到文件，SIGTERM 前已写入
timeout 180 bash /root/start.sh > /tmp/verify.log 2>&1
tail -50 /tmp/verify.log
```

**教训**

- 排查"命令跑不起来"时，**永远先重定向到文件**，不要用管道
- `timeout` + 管道 = 必然丢输出

### 1.4 `GRASP_SAMPLER_READY` 从未打印（采样器静默失效）

**现象**

训练能跑，loss 也降，但日志里搜不到 `GRASP_SAMPLER_READY`。

**原因**

`enable_alltask_grasp.py` 的 `patch_source()` 做的是：

```python
dest = LOCAL / 'source'
shutil.copytree(SOURCE, dest, ignore=...)
p = dest / 'lingbotvla/data/vla_data/multi_vla_dataset.py'
text = text.replace(needle, needle + '        idx = self._grasp_phase_index(idx)\n') + SAMPLER_CODE
```

也就是**复制一份 source 到 `LOCAL/source`，只在副本里打补丁**。

但启动脚本里的 `PYTHONPATH` 仍指向**原始** `SOURCE`，于是 Python import 的是没打补丁的版本 → 补丁静默失效，采样率实际是 0%。

**修复**

```bash
export PYTHONPATH=/root/work/cont1020/source   # ← 必须指向 patched 副本
```

并在启动后 grep 日志确认：

```bash
grep 'GRASP_SAMPLER_READY' /teams/.../logs/cont1020-p50.log
# 期望：GRASP_SAMPLER_READY: within-task probability=0.50
```

**教训**

- 任何"打补丁式"的改动，**必须有运行时的自证日志**（print 一行 `XXX_READY`），否则你无法区分"补丁生效但没效果"和"补丁根本没加载"

### 1.5 备份脚本 `prune` 逻辑导致死循环

**现象**

```
12:38  prune global_step_4000
12:38  prune global_step_4500
12:39  backing up global_step_4000
12:42  DONE global_step_4000
12:45  backing up global_step_4500
12:48  prune global_step_4000      ← 又删了
12:49  backing up global_step_4000  ← 又备份
...
```

40 分钟一直在搬同一批文件，磁盘从 64 GB 降到 31 GB。

**错误代码**

```bash
# ❌ 按「团队盘自身」排序删多余的 —— 和本地盘不同步，导致删了又被备份回来
ls -d "$DST"/global_step_* | sort -V | head -n -2 | xargs -r rm -rf
```

**正确思路**

```bash
# ✅ 以本地盘为准：只保留本地最新的 N 个，团队盘上不在这 N 个里的才删
# ✅ 或者记录已备份清单，而不是靠「目录是否存在」判断
```

**教训**

- 备份/清理逻辑必须**单一事实来源**（以本地盘为准），否则两个盘互相"纠正"会死循环
- 清理脚本上线前，先 `echo` 出它要删什么，人工看一遍

### 2.1 `FileNotFoundError: .../global_step_6000/model/__0_8.distcp`

**完整报错**

```
FileNotFoundError: [Errno 2] No such file or directory:
'/teams/A100_zone_1791964949/robotwin_cuda/training_runs/multi50-cont-1020/output/checkpoints/global_step_6000/model/__0_8.distcp'
```

**原因**

`rsync` 按**字典序**遍历目录：

```
__0_0, __0_1, __0_10, __0_11, __0_12, __0_13, __0_14, __0_15, __0_2, __0_3, __0_4, __0_5, __0_6, __0_7, __0_8, __0_9
```

备份在 `__0_7` 之后被 `pkill` 中断 → 缺 `__0_8` 和 `__0_9`（3.2 GB）。

备份脚本的"完整性检查"只看 `model/.metadata` 和 `optimizer/.metadata` —— 这两个文件是**先写**的，所以检查通过，但数据不完整。

**诊断**

```bash
D=/teams/.../global_step_6000
ls "$D/model/" | wc -l          # 应该 17（.metadata + 16 个 distcp）
find "$D" -type f -printf '%s\n' | awk '{s+=$1} END {printf "%.2f GB\n", s/1e9}'
# 完整应该是 25.64 GB（23.2 + 0.03 + 0.000008）
```

**教训**

- 判断 ckpt 完整性的**唯一可靠方法**：`tar tf`（对 tar）或**文件数 + 总字节数**（对目录）
- `.metadata` 存在 ≠ 数据完整，metadata 是最先写入的

### 2.2 `ls -ld` 的 size 列在 fx 文件系统上不可靠

**现象**

```
$ ls -ld /teams/.../some_dir
drwxr-xr-x 1 root root 22355573734 Oct 21 10:34 .     ← 22 GB？一个目录？
```

**原因**

`fx`（矩池云团队盘的 FUSE 文件系统）报告的目录 size 是元数据块大小，不是内容大小。`du` 也返回 0。

**正确算法**

```bash
find "$DIR" -type f -printf '%s\n' | awk '{s+=$1} END {printf "%.2f GB\n", s/1e9}'
```

**教训**

- 在 fx 上，**`ls -ld` 和 `du` 都不能信**，只有 `find -printf '%s'` 求和可靠
- 删了"34.8 GB"实际只释放 6 GB 的情况也遇到过 —— 同一个原因

## 三、文件传输

### 3.1 `scp` 长传中断（0.49 GB 卡了 7.5 小时）

**现象**

```
00:23  upload=0.41GB
06:03  upload=0.49GB
07:53  upload=0.49GB      ← 7.5 小时一个字节没动
```

**原因**

1. **笔记本休眠** —— Windows 默认 15-30 分钟无操作就睡，`scp` 连接被断
2. `scp` 不支持续传，断了只能重来
3. 没有心跳机制，NAT 也会主动断空闲连接

**修复**

```powershell
# ① 禁止休眠
powercfg /change standby-timeout-ac 0
powercfg /change monitor-timeout-ac 0
powercfg /change hibernate-timeout-ac 0

# ② 关键：禁止合盖休眠（正确语法，注意不是 /change lid-close-action-ac）
powercfg /setacvalueindex SCHEME_CURRENT 4f971e89-eebd-4455-a8de-9e59040e7347 5ca83367-6e45-459f-a27b-476b1d01c936 0
powercfg /setactive SCHEME_CURRENT

# ③ 加心跳
scp -P 29212 -o ServerAliveInterval=30 -o ServerAliveCountMax=20 src dst
```

**教训**

- 传大文件前，**先设好电源策略**，否则笔记本一睡就白费
- `-o ServerAliveInterval=30` 是必须的，不是可选的

### 3.2 `sftp reput` 极慢（10–208 KB/s，ETA 100+ 小时）

**现象**

```
sftp> reput ckpt6500.tar
Resuming upload of ckpt6500.tar to /root/ckpt6500.tar
ckpt6500.tar   68%  16GB   21.3KB/s  101:59:04 ETA
ckpt6500.tar   68%  16GB   10.2KB/s  - stalled
```

**原因**

`reput` **功能上确实支持续传**（读远程文件大小 N，从本地偏移 N 处 append），
但 OpenSSH sftp 用 32 KB 的 block + 小 window，**在高延迟链路上吞吐暴跌，比 scp 慢 200 倍**。

**结论**

**sftp reput 不可用于大文件续传。** 功能正确 ≠ 实际可用。

**替代方案（按推荐度）**

| 方案 | 命令 | 说明 |
|---|---|---|
| **WSL rsync** | `wsl rsync -avP --partial --append-verify -e "ssh -p PORT" src dst` | 最优，自动续传 + 校验 |
| **精确切块 + scp** | PowerShell `FileStream.Seek` + `scp` | 次优，无需安装，本文档采用 |
| **scp 重传** | `scp src dst` | 最笨但最可靠 |

**教训**

- 给方案前要**同时验证"功能"和"性能"**，只验证功能会给出不可用的建议

### 3.3 重跑 `scp` 会从头覆盖（不续传）

**现象**

```
第一次 : part2.7.bin  63%  598MB  101.0KB/s  59:04     ← Ctrl+C 停了
第二次 : part2.7.bin   8%   83MB  212.2KB/s  1:09:32   ← 从 0 重新开始
```

**原因**

`scp` 打开目标文件用 `O_WRONLY|O_CREAT|O_TRUNC` → 一旦开始写就清空。

**⚠️ 但有一个可利用的窗口**：`scp` 在**认证/握手阶段还没 truncate**。如果在这之前 Ctrl+C，云端文件保持原大小。

**正确做法**

需要续传时，**不要重跑 scp**，而是：

```powershell
# ① 云端取精确大小
stat -c %s /root/bigfile.bin

# ② 本机从该偏移切出剩余
$offset = <上面的数字>
$fs = [System.IO.File]::OpenRead("D:\path\bigfile.bin")
$fs.Seek($offset, 'Begin') | Out-Null
$out = [System.IO.File]::Create("D:\path\bigfile.part2.bin")
$buf = New-Object byte[] (8388608)
while (($n = $fs.Read($buf, 0, $buf.Length)) -gt 0) { $out.Write($buf, 0, $n) }
$fs.Close(); $out.Close()

# ③ 传那一块
scp -P 29212 bigfile.part2.bin root@host:/root/

# ④ 云端拼接
cd /root && cat bigfile.part2.bin >> bigfile.bin && rm bigfile.part2.bin
```

**教训**

- `scp` **不支持续传**，别再重跑它期望"接着传"
- 中断前先 Ctrl+C（让文件停在完整前缀），别等它自己断

### 3.4 `Connection reset` / `Broken pipe`

**现象**

```
client_loop: send disconnect: Connection reset
C:\Windows\System32\OpenSSH\scp.exe: Couldn't send packet: Broken pipe
```

**原因**

- 笔记本休眠 / 断网 / 切换 WiFi
- 网络抖动导致 TCP 连接被 RST

**修复**

同 3.1（电源策略 + 心跳参数）。

**补充：分块并行上传（实测有效）**

单流 317 KB/s 限速时，8 个并行 scp 每个仍能跑 ~280 KB/s，合计约 2.2 MB/s，**快 7 倍**。

```powershell
# 切 8 块（PowerShell，内存安全）
$src = "D:\ckpt\part2.bin"; $n = 8
$fs = [System.IO.File]::OpenRead($src); $size = $fs.Length
$chunk = [int64][math]::Ceiling($size / $n)
$buf = New-Object byte[] (8388608)
for ($i=0; $i -lt $n; $i++) {
  $start = [int64]($i * $chunk)
  $remain = [math]::Min($chunk, $size - $start)
  if ($remain -le 0) { break }
  $fs.Seek($start, 'Begin') | Out-Null
  $out = [System.IO.File]::Create("D:\ckpt\part2.$i.bin")
  while ($remain -gt 0) {
    $want = [int][math]::Min([int64]$buf.Length, $remain)
    $r = $fs.Read($buf, 0, $want); if ($r -le 0) { break }
    $out.Write($buf, 0, $r); $remain -= $r
  }
  $out.Close()
}
$fs.Close()

# 云端按序拼接
# for i in 0 1 2 3 4 5 6 7; do cat part2.$i.bin >> ckpt6500.tar; done
```

**⚠️ 拼接前必须校验：**

```bash
stat -c %s /root/ckpt6500.tar      # 必须等于本地文件字节数
tar tf /root/ckpt6500.tar > /dev/null && echo "✅ tar 完整" || echo "🔴 损坏"
```

**教训**

- 大文件传输的**第一选择是分块并行**（能突破单流限速，且单块失败只重传一块）
- 别指望工具帮你续传，自己切块最可控

### 5.3 PowerShell 把「解释文字」当命令执行

### 5.4 `pgrep -af 'a' 'b'` → `only one pattern can be provided`

**现象**

```
$ pgrep -af 'torch.distributed.run' 'train_lingbotvla'
pgrep: only one pattern can be provided
```

**修复**

```bash
# ❌ 错误
pgrep -af 'a' 'b'

# ✅ 正则 OR
pgrep -af 'a|b'

# ✅ 或者分开跑
pgrep -af 'a'; pgrep -af 'b'
```

**⚠️ 另一个坑**：`pgrep -f 'pattern'` 会匹配到自己的命令行 → 用字符类打断：

```bash
pgrep -af '[t]orch.distributed.run'    # 不会匹配到 pgrep 自己
```

### 5.5 `grep -iE 'Traceback'` 假阳性

**现象**

排查脚本每次都报"有 Traceback"，但训练其实正常。

**原因**

匹配到了 transformers 的警告：

```
UserWarning: Enable tracemalloc to get the object allocation traceback
```

**修复**

```bash
# ❌ 太宽
grep -iE 'Traceback'

# ✅ 精确
grep -cE 'Traceback \(most recent call last\)|ChildFailedError|CUDA out of memory'
```

## 七、教训总结（按重要性）

### 1. 报错信息经常"指向错误的组件"

| 报错 | 真因 |
|---|---|
| `HFValidationError: Repo id must be in the form...` | **路径不存在**，不是 HF 认证问题 |
| `FileNotFoundError: __0_8.distcp` | **备份被中断**，不是代码 bug |
| `AttributeError: right_planner` | **显存不足**，不是 API 变了 |
| `参数无效` (powercfg) | **语法不对**，不是权限问题 |

**→ 看报错时先问："它说的这个东西，真的存在吗？"**

---

### 2. 「功能正确」≠「实际可用」

**sftp reput 是典型案例**：文档说支持续传，实际慢 200 倍。

**→ 给方案前要同时验证功能和性能。**

---

### 3. 自动化脚本必须有「自证日志」

`GRASP_SAMPLER_READY` 这个 print 的价值极高 —— 它让我们能在 10 秒内确认补丁生效，而不是花 2 小时调参才发现采样率是 0%。

**→ 任何"打补丁/改配置"的改动，都加一行 `XXX_READY` 日志。**

---

### 4. 笔记本会睡，网络会断，工具不支持续传

**→ 大文件传输：先设电源策略 + 心跳参数 + 分块（单块失败只重传一块）。**

---

### 5. 备份完整性只能靠「字节数 + 结构校验」

`.metadata` 存在 ≠ 数据完整。**必须 `tar tf` 或「文件数 + 总大小」双重确认。**

---

### 6. 命令块要标清「在哪跑」

`PS C:\...>` vs `(base) -bash-5.1#` —— 这个混淆在本次项目里出现了**至少 6 次**，是最浪费时间的问题。

**→ 每条命令前标注环境，说明文字单独放。**
